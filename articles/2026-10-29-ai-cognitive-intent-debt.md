## はじめに

University of Victoria の Margaret-Anne Storey 教授は、起業家育成の授業で次のような場面に出会ったそうです。

学生チームが生成 AI を使って、ものすごい速度で機能を出荷していました。ところが8週目あたりで急に手が止まります。小さな変更で思わぬ場所が壊れ、進捗が止まってしまったのです。学生たちは最初「技術負債のせいだ」と考えました。しかし掘り下げてみると、本当の問題は別のところにありました。**チームの誰も、なぜその設計にしたのか、各部分がどう連携するはずなのかを説明できなかった**のです。判断の理由もどこにも書き残されていませんでした。

Storey はこの体験をもとに、ソフトウェアの健全性を3種類の負債で捉える **三重負債モデル（Triple Debt Model）** を提案しています。

- [From Technical Debt to Cognitive and Intent Debt: Rethinking Software Health in the Age of AI（arXiv:2603.22106）](https://arxiv.org/abs/2603.22106)

この論文の主張を一言でまとめると、**「生成 AI は技術負債を減らしながら、認知負債と意図負債の蓄積を加速させているかもしれない」** というものです。

本記事では、三重負債モデルの中身を整理したうえで、論文が挙げる診断の兆候と対策を **Claude Code の日常運用（CLAUDE.md、skills、Plan Mode など）にどう落とし込むか** を考えます。

## 三重負債モデル：負債には3つの置き場所がある

Storey は、ソフトウェアシステムは次の3つの層にまたがって存在すると述べています。

1. **目標と意図**: システムが満たすべき要件・制約・目的。仕様、テスト、ドキュメントに記録されるもの
2. **コードと構造**: 意図を実装したもの。ソースコード、アーキテクチャ、依存関係、インフラ
3. **共有された理解**: 開発者や PM などが持つ「システムがどう動き、どう推論できるか」のメンタルモデル。Peter Naur が「プログラムの理論（theory）」と呼んだもの

従来の「技術負債」は2番目の層の問題だけを指していました。三重負債モデルでは、残りの2つの層にもそれぞれ負債がたまると考えます。

| 負債 | 置き場所 | たまる条件 | 制限されるもの |
|---|---|---|---|
| 技術負債 | コード | 実装上の判断が将来の変更しやすさを損なう | システムをどう変えられるか |
| 認知負債 | 人（チーム） | 共有理解が補充されるより速く失われる | 変更についてどこまで推論できるか |
| 意図負債 | コード以外の成果物 | 目標や制約が記録・維持されていない | システムが本来の目的を保てるか、人と AI エージェントが進化させられるか |

論文はこれを「技術負債はシステムを変えにくくし、認知負債は理解しにくくし、意図負債は何のためのシステムなのかを分からなくする」と対比させています。

### 3つの負債は互いに増幅し合う

ポイントは、これらが独立していないことです。

- **意図負債 → 認知負債**: 目的が書かれていないと、新メンバーや久しぶりに戻ったメンバーが正しいメンタルモデルを作れない
- **認知負債 → 意図負債**: 意図を理解していない人は、仕様や判断理由を書き残せない
- **認知負債 → 技術負債**: 理解していない人は、まずい実装判断をしやすい
- **技術負債 → 認知負債**: 汚いコードは推論しにくく、理解をさらに削る

つまり、技術負債だけを測って管理していても、残り2つの負債が裏で膨らんでいれば、いずれ技術負債にも跳ね返ってきます。

## AI が負債のバランスをどう変えるか

### 技術負債は減らせる

論文は、技術負債の管理については AI に大きな可能性があると認めています。自動リファクタリング、AI によるコードレビュー、テスト生成などで、技術負債は減らしやすくなりました。

### 「書く」と「理解する」の結びつきが切れる

一方で、認知負債については逆向きの力が働きます。人間がゼロからコードを書くと、たとえ汚いコードでも、その過程の摩擦と労力によって少なくとも部分的なメンタルモデルができあがります。AI が同じコードを生成した場合、開発者はそれと同じだけの理解を作らずに受け入れてしまうことがあります。

従来、チームから理解が失われる典型的なきっかけは「詳しい人の離職」でした。AI 時代には、**誰も辞めていないのに理解が失われる** ことが起こりえます。

### 認知的降伏（cognitive surrender）

論文は、この背後にある心理的メカニズムとして、Shaw と Nave が提唱する **認知的降伏（cognitive surrender）** を引いています。AI の出力をほとんど吟味せずに採用し、直感も熟慮も飛ばしてしまう状態のことです。

ここで大事なのは、**認知的オフロード** との区別です。

- **認知的オフロード**: linter や型チェッカーのように、範囲のはっきりしたタスクを道具に任せること。合理的な生産性の選択です
- **認知的降伏**: 判断そのものを AI の流暢な出力に明け渡してしまうこと

さらに厄介なのは、認知的降伏が AI が間違っているときでも自信を高めてしまう、という指摘です。チームは実際より理解しているつもりになるので、認知負債は手遅れになるまで見えません。

### 意図負債は「後から返せない」

論文が特に強調しているのが意図負債です。AI エージェントは書かれた意図しか読めません。意図が書かれていなければ、エージェントは技術的には正しいけれど的外れな方向に最適化します。

そして意図負債には、技術負債にはない性質があります。**意図は判断したその瞬間に記録するのが最善で、後から復元するのは難しく、不可能な場合もある** という点です。汚いコードは後からリファクタリングできますが、「なぜこうしたのか」は当事者の記憶から消えたら戻ってきません。

## 実証データ：速くならないのに、理解は下がる

この議論を裏付ける実験として、Anthropic が2026年1月に公開した RCT（ランダム化比較試験）があります。

- [How AI assistance impacts the formation of coding skills（Anthropic）](https://www.anthropic.com/research/AI-assistance-coding-skills)
- 論文: [arXiv:2601.20245](https://arxiv.org/abs/2601.20245)

実験の概要は次のとおりです。

- 参加者は主にジュニアのソフトウェアエンジニア52名
- 初めて触る Python の非同期ライブラリ Trio を使った課題を解く
- AI アシスタントを使う群と、手で書く群に分ける
- 課題の直後に、今使った概念についてのクイズを受ける

結果は次のとおりでした。

| 指標 | AI 群 | 手書き群 |
|---|---|---|
| クイズの平均スコア | 50% | 67% |
| 作業時間 | 約2分速い（統計的に有意ではない） | — |

理解度の差は統計的に有意（p=0.01）でしたが、速度の差は有意ではありませんでした（p=0.391）。**少なくともこの実験条件では、AI を使っても有意には速くならず、理解度だけが下がった** ことになります。

### 差を分けたのは「AI の使い方」

ただし、この研究で一番示唆に富むのは、AI 群の中でも使い方によって結果が大きく分かれたことです。

| パターン | 内容 | 平均スコア |
|---|---|---|
| 概念的な質問 | 概念だけを AI に質問し、コードは自分で書く | 65%以上 |
| 生成してから理解 | 生成させた後、追加の質問で理解を深める | 65%以上 |
| コードと説明の併用 | コード生成と同時に説明も求める | 65%以上 |
| AI への全面委任 | コード作成をすべて AI に任せる（最速） | 40%未満 |
| 段階的な依存 | 最初は質問していたが、次第に全部任せる | 40%未満 |
| 反復的な AI デバッグ | 理解のためでなく、動かすために AI に頼る | 40%未満 |

各パターンの人数は2〜7名と少なく、因果関係までは示されていません。それでも、**AI を「理解を作るため」に使うか「理解を省くため」に使うか** で結果が変わるという傾向は、認知負債の議論とよく合っています。

:::message
この研究の限界も押さえておきましょう。測定は課題直後の理解度だけで、長期的なスキル習得は追っていません。また、実験環境は Claude Code のようなエージェント型ツールとは異なります。
:::

## 意図負債を返す：意図を「エージェントが読める成果物」にする

ここからが本題です。論文が挙げる意図負債の対策は、次の3種類の「生きた成果物」に投資することでした。

1. **実行できる意図**: 振る舞いを確かめるだけでなく、目的を表現するように書いた BDD 仕様やテスト
2. **判断と理由の記録**: ADR（Architectural Decision Records）や、DDD のユビキタス言語
3. **AI 支援開発のためのコンテキスト成果物**: skills、エージェントへの指示、プレイブック

3番目は、Claude Code ユーザーにとってそのまま日常の道具です。

### CLAUDE.md は「意図負債の返済台帳」

CLAUDE.md は、Claude Code がセッションのたびに読み込む指示ファイルです。ここに何を書くかで、エージェントに渡る意図が決まります。

ありがちなのは、CLAUDE.md に「何をするか（What）」だけを書いてしまうことです。

```markdown
# 悪い例: 規則だけで理由がない
- main ブランチに直接 push しない
- 金額は number ではなく Decimal で扱う
- 認可の判断は PDP に問い合わせる
```

これだと、エージェントは規則には従えても、規則がカバーしていない場面では判断できません。意図負債を返すには、**なぜそうするのか（Why）と、何を守りたいのか（制約）** を書きます。

```markdown
# 良い例: 理由と守りたいものを書く
## 公開フロー
main への push は Zenn に即時公開されるため、直接 push は禁止。
必ず PR を作り、人間のレビューを通してからマージする。

## 金額の扱い
請求額の端数誤差は顧客との信頼問題になるため、金額は Decimal で扱う。
浮動小数点で計算している箇所を見つけたら、修正を提案すること。

## 認可
認可ロジックをアプリ側に分散させると監査できなくなるため、
判断は必ず PDP に問い合わせる。トークンに権限を詰め込まない。
```

理由が書いてあれば、エージェントは「この新しいケースは、守りたいもの（信頼・監査可能性）に照らすとどうすべきか」を推論できます。論文の言う、エージェントが **「システムが今何をしているか」だけでなく「何のためにあるのか」** を理解できる状態です。

### skills は「判断の手順」を外部化する

`.claude/skills/<name>/SKILL.md` に置く skills は、繰り返し行う作業の手順を書いておく仕組みです。この記事を書いているリポジトリでも、記事の公開フローやリサーチの手順を skills にしています。

skills を書くときも、手順の羅列だけでなく、**各手順がなぜ必要なのか** を添えておくと意図負債の返済になります。たとえば「Web 検索の結果をそのまま事実として書かない」というルールなら、「検索結果のスニペットは公式由来とは限らないから」という理由を添えます。理由があれば、エージェントはルールに書かれていない似た状況（たとえば別のまとめサイトの数値）にも同じ判断を広げられます。

### ADR とテストは「判断したその場で」書く

意図負債は後から返せません。だからこそ、**判断が起きたその場で記録する** 仕組みが大事です。

Claude Code で設計判断をしたセッションの終わりに、次のように頼む習慣をつけるのがおすすめです。

```text
今回のセッションで決めた設計判断を ADR として docs/adr/ に書いて。
「決めたこと」「理由」「検討したが採用しなかった案とその理由」を必ず含めること。
```

「採用しなかった案」が特に重要です。後から別の人（あるいは別のエージェント）が同じ案を再提案して、同じ議論を繰り返すのを防げます。

テストも同様です。テスト名を `test_calc_2` ではなく、**守りたい意図を表す名前** にしておくと、テストが落ちたときに「どの意図からずれたのか」がわかります。論文の言う「実行できる意図」です。

```python
# 意図が読み取れないテスト名
def test_invoice_calc_2(): ...

# 意図を表すテスト名
def test_請求額は明細の合計を円未満切り捨てで計算する(): ...
```

:::message
筆者は以前、業務委託の現場で「動画の台本」を仕様の中心に置くやり方を書きました。これも、顧客の意図を合意できる形で外部化して意図負債をためない工夫の一つと言えます。
[要件が曖昧な業務委託は「動画の台本」を仕様にする](https://zenn.dev/ino_h/articles/2026-10-07-contract-work-video-script-as-spec)
:::

## 認知負債を返す：理解を「成果物」として扱う

論文は実践への示唆の筆頭に **「理解を成果物（deliverable）として扱う」** ことを挙げています。動くコードと同じように、共有理解も明示的に投資する対象だという考え方です。

### Plan Mode の出口を「理解の確認ポイント」にする

Claude Code の Plan Mode は、実装前に計画だけを作らせるモードです（詳しくは [Plan Mode 中心の Claude Code 開発手法](https://zenn.dev/ino_h/articles/2026-05-01-claude-code-plan-mode-workflow) にまとめています）。

Plan Mode を「AI に計画を立ててもらう場」だけで終わらせず、**自分が理解したかを確かめる関門** として使うと、認知負債の予防になります。計画を承認する前に、次のことを自問します。

- この計画を、AI の文章を見ずに自分の言葉で同僚に説明できるか
- 変更で影響を受けるのはどのモジュールか、自分で言えるか
- この方針を選んだ理由と、選ばなかった案を言えるか

説明できないなら、承認せずに AI に質問を返します。Anthropic の実験で高得点だった「生成してから理解」「概念的な質問」のパターンを、意図的に計画段階に組み込むイメージです。

```text
この計画で、既存の認可処理のどこが変わるのか、
変更前と変更後の処理の流れを箇条書きで比較して説明して。
```

### 書いていないコードを説明するウォークスルー

論文が認知負債の対策として挙げているものの一つに、**自分が書いていないコードを開発者が説明するウォークスルー** があります。目的はドキュメント作りでもリファクタリングでもなく、知識の共有と Naur の言う「理論構築」です。

AI が生成したコードは、ある意味で「チームの誰も書いていないコード」です。マージされた AI 生成の変更から週に1つ選び、担当者が AI の助けを借りずに数分で説明する。こうした小さな儀式が、共有理解の補充になります。

### 再実装で理解を取り戻す

論文が挙げている対策の中で、AI 時代ならではのものが **再実装** です。コード生成のコストが下がった今、理解を失った機能を、別のテストや別の設計でエージェントに作り直させることで、理解を再構築できるとしています。

生成されたコードそのものより、「なぜ前の設計ではこうなっていたのか」を新旧の比較から学ぶことに価値があります。

## 「理解の自動化」に抗う

ここで一つ、大きな落とし穴があります。論文はこれを **「理解の自動化に抗え（Resist the automation of understanding）」** と表現しています。

AI にコードだけでなくドキュメントまで生成させると、チームが本当の理解を作らないまま「システムが何をするか」の説明文だけが増えていきます。**理解の見せかけが本物の理解の代わりになり、認知負債がかえって見つけにくくなる** という指摘です。

Claude Code で言えば、たとえば `/init` で CLAUDE.md を自動生成するのは便利な出発点です。しかし、生成された内容をそのまま置いておくだけでは、それは「コードから読み取れる What の要約」にすぎず、意図負債はほとんど返済されていません。自動生成したら、**コードからは読み取れない Why と制約を人間が書き足す** ところまでがセットです。

> velocity without understanding is not sustainable
>
> — Margaret-Anne Storey, [cognitive debt](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/)

AI に説明させること自体は悪くありません。問題は、説明を読んだだけで理解したつもりになることです。図や比較表で説明させるのは理解を助けますが、最後に「自分の言葉で言い直せるか」を確かめる人間側の摩擦は残しておく必要があります。

## 兆候チェックリスト

論文が挙げる診断の兆候を、チェックリストにまとめました。チームの振り返りで使ってみてください。

### 認知負債の兆候

- [ ] **変更をためらう**: システムを理解している自信がなく、誰も触りたがらない箇所がある
- [ ] **予想外の結果**: 変更したとき、期待したのとまったく違う結果が出ることがある
- [ ] **オンボーディングが遅い**: ドキュメントはあるのに新メンバーが立ち上がらない（ドキュメントが What しか書いておらず Why がない）
- [ ] **「誰が何を知っているか」が分からない**: チームの共有の場ではなく、各自が AI との個別のやりとりで解決している
- [ ] **バス係数が低い**: システムを本当に理解しているのが1人か2人だけ

### 意図負債の兆候

- [ ] **振る舞いのずれ**: 関係者が思っている動作と実際の動作が食い違い、テスト段階や障害で初めて発覚する
- [ ] **AI エージェントが苦戦する**: 確認の質問が多い、技術的には正しいが的外れな解決策を出す、想定よりトークンや時間を使う
- [ ] **制約が忘れられる**: 性能予算、プライバシー、アクセシビリティなどの非機能要件を一部の人しか知らない

AI エージェントの苦戦が意図負債の兆候として挙げられているのは面白い点です。**Claude Code が何度も的外れな変更をしてくるなら、プロンプトの問題ではなく、リポジトリの意図負債が表面化している** のかもしれません。

## 論文自身が認めている未解決の論点

公平のために、論文が「議論の余地がある」として挙げている点も紹介します。

- **意図を文書化すべきか**: 「どう来たかはどうでもよく、必要なことは再構築できる」と考える実務家もいます
- **AI で暗黙知を形式知にできるか**: ドキュメント作成の価値は、書く過程で得られる人間の理解にこそあるという反論があります
- **負債はリスクか戦略か**: マネージャーがチームを信頼してきたように、実装の詳細まで理解する必要はないという立場もあります

また、この論文は実験ではなく、既存研究を統合した概念モデルです。三重負債モデルを「測定済みの事実」ではなく、**チームで負債を語るための共通言語** として使うのがよいでしょう。

## まとめ

- 生成 AI は技術負債を減らす一方で、**認知負債（人に宿る、共有理解の侵食）** と **意図負債（成果物に宿る、目標・制約・理由の欠落）** の蓄積を加速させる可能性があります
- 3つの負債は互いに増幅し合うため、測りやすい技術負債だけを管理していても不十分です
- Anthropic の実験では、AI を使っても有意には速くならず、理解度は下がりました。ただし、AI を理解のために使った人は高い理解度を保っていました
- 意図負債は後から返せないので、**CLAUDE.md や skills に Why と制約を書き、判断したその場で ADR を残す** のが効果的です
- 認知負債は、**Plan Mode の出口を理解の確認ポイントにする**、ウォークスルーや再実装で理解を補充する、といった形で返していけます
- AI にドキュメントを生成させて **理解したつもりになる「理解の自動化」** には注意が必要です

Storey は論文の結びで、ソフトウェアチームはコードと同じだけの注意と緊急性をもって「理解」を管理すべきだと述べています。AI でコードを書く速度が上がった今こそ、意図と理解に投資する時間を意識的に確保していきましょう。
