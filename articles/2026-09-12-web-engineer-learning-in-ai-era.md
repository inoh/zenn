## はじめに

AIコーディングツール（Claude Code、Cursor、Copilot など）が当たり前になり、「コードを書く」というスキルの相対的な価値が下がってきました。では Web エンジニアは今、何を学べばいいのでしょうか。

本記事では、この問いを Claude Code と対話しながら整理した内容をまとめます。特に途中で出てきた **「AIは膨大なコードを生成するのに、レビューなんて現実的に無理では？」** という素朴な疑問と、それに対する答えが本記事の核心です。

## 1. 価値が上がっているスキル

### 設計・要件定義・意思決定

コードを書くコストが下がった分、「何を作るか」「どう分割するか」「トレードオフをどう判断するか」の比重が上がっています。システム設計、ドメインモデリング、API 設計、データモデリングは今まで以上に重要です。

### コードを「読んで評価する」力

AI が生成したコードの正しさ・セキュリティ・保守性を判断できないと、生成量に品質が追いつきません。「書く」時間より「読んで評価する」時間が増えます（ただし、これには後述する重要な但し書きがあります）。

### テスト・検証の設計

AI の出力の妥当性を担保する手段は、結局テストと観測です。テスト設計、E2E、契約テスト、observability（ログ・メトリクス・トレース）は投資対効果が高い領域です。

### 変わらない基礎

HTTP、認証認可、ブラウザの仕組み、DB、並行処理など。フレームワークは変わってもここは変わらず、AI の出力を判断する土台になります。

## 2. AI を「使う側」のスキル

- **AI コーディングツールの実践的な活用** ― プロンプトの書き方そのものより、タスク分割・コンテキスト設計・検証ループの回し方が肝です
- **LLM アプリ開発の基礎** ― Messages API、tool use、RAG、エージェント設計、MCP、評価（eval）。全員が AI エンジニアになる必要はありませんが、Web アプリに LLM を組み込む場面は確実に増えます
- **コスト・レイテンシ・非決定性を前提としたプロダクト設計**

## 3. 相対的に価値が下がっているもの

- 特定フレームワークの細かい API の暗記
- ボイラープレートを速く書く能力
- 定型的な CRUD 実装のスピード

「知っている」から「判断できる」へ軸足を移す、という感覚です。

## 4. 「生成コード」とは何を指すのか

ここで一度、用語を整理しておきます。「生成コード」とは AI ツールが書いたコード全般のことで、言語は問いません。Web エンジニアなら実際にはこういう場面が多いはずです。

- **TypeScript / React** ― 「このフォームにバリデーション追加して」と頼んで出てきたコンポーネント
- **バックエンド（Node.js / Python / Go など）** ― API エンドポイントや DB アクセス層
- **SQL** ― 「このテーブルから月別集計を出すクエリを書いて」の結果
- **テストコード** ― 既存関数のユニットテスト生成
- **設定ファイル** ― CI 設定、Nginx 設定、Terraform など

これらに対して、例えば次のような点を確認する必要があります。

- SQL に N+1 やインデックスを効かせない書き方が混ざっていないか
- 認証チェックが抜けていないか、ユーザー入力をそのまま使っていないか
- 存在しないライブラリの API を呼んでいないか（AI はたまに架空の関数を書きます）
- テストが「通るように書かれただけ」で実質なにも検証していないか
- 既存コードの規約やパターンと矛盾していないか

## 5. 「でも、全部読むのは現実的じゃない」

ここが本題です。

AI は一度に数百〜数千行を平気で生成します。それを人間が全行レビューするのは、率直に言って**破綻します**。「生成コードをレビューしよう」という助言は、そのままでは実行不可能です。

では現場ではどうしているか。答えは「**レビューの粒度と手段を変える**」です。人間が読むのは、ごく一部だけです。

### 5-1. 読む場所を絞る

全部読むのではなく、壊れると困る箇所だけ人間が見ます。

- 認証・認可・課金・データ削除など、ミスの代償が大きい部分
- 外部との境界（API の入出力、DB スキーマ、公開インターフェース）
- 設計判断が入っている部分（どう分割したか、どこに状態を置いたか）

UI の細かい実装や定型的な CRUD は、動作確認とテストで代替します。

### 5-2. 「コード」ではなく「結果」を検証する

- テストを先に書かせる／自分で書いて、それが通るかで判断する
- 型チェック・lint・静的解析を自動で通す
- 実際に動かして触る

コードを読まなくても品質を担保できる仕組みがあれば、読む必要はありません。

### 5-3. AI にレビューさせる

生成したのとは別のセッション、あるいは別のモデルにレビューさせる運用が普通になってきています。Claude Code には `/code-review` や `/security-review` があり、diff に対して指摘だけを出させられます。

人間がやるのは「指摘の妥当性を判断する」ことだけ。これは全行読むより圧倒的に軽い作業です。

### 5-4. 生成の単位を小さくする

**これが一番効きます。**

一度に 1000 行生成させてからレビューするのではなく、小さいタスクに分けて都度確認しながら進める。膨大になるのは「丸投げしたから」であることが多いです。

## 6. 「学ぶべきこと」の言い直し

以上を踏まえると、「生成コードを読む力」という表現は不正確でした。より正確には、

- **どこが危険かを見抜いて、読む場所を選ぶ判断力**
- **読まなくても品質を担保できる仕組み（テスト・型・CI・自動レビュー）を組む力**
- **AI に任せる粒度をコントロールする力**

です。

よく考えると、これは昔からあった原則そのものです。

- 大きな PR はレビューできない → 小さく分けろ
- テストのないコードは信用しない
- 境界と危険箇所に集中しろ

AI 時代になって新しい原則が生まれたわけではなく、**既存の原則の重要性が一段上がった**、というのが実態だと思います。

## おわりに

実際の現場では、経験の浅いエンジニアが AI で大量生成して手に負えなくなる一方、ベテランは小さく切って検証しながら進めるので速くて安全、という差がかなり出ています。

差がつくのは「コードを読む速度」ではなく、**運用設計**のところです。

学習の優先順位としては次の順番をおすすめします。

1. 普段の業務で AI ツールを本気で使い、危険箇所を見極めてレビューする習慣をつける
2. 小さな LLM 組み込み機能を 1 つ作って運用してみる
3. 設計本を 1 冊読み込む（『データ指向アプリケーションデザイン』『Clean Architecture』など）
4. 自分のドメイン（業務領域）知識を深める ― AI はドメイン文脈を持たないので、ここが差別化になります

インフラ・セキュリティ・パフォーマンスチューニングなど「壊れると困る領域」も、AI に任せきれないため需要は堅いでしょう。

「知っている」より「判断できる」へ。それが AI 時代の Web エンジニアに求められる方向性だと考えています。
