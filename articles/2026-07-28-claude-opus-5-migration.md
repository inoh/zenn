## はじめに

2026年7月24日に Claude Opus 5 が公開されました。価格は Opus 4.8 と同じ $5 / $25（100万トークンあたりの入力 / 出力）に据え置かれています。

先に誤解しやすい点を潰しておくと、**1M トークンのコンテキストは Opus 5 の新要素ではありません**。Opus 4.8 も 4.7 も 4.6 も、Sonnet 5 / 4.6 もすでに 1M です。最大出力 128k も価格も 4.8 と同じで、スペック表を並べても差がほとんど出ません。

ベンチマークの数字はすでに各所で紹介されています。この記事で扱いたいのはその先です。**Opus 5 への移行作業の本体は、プロンプトに何かを足すことではなく、4.8 時代に書いた指示を消すことでした。**

公式ドキュメントは Opus 5 について、こう書いています。

> removing them reduces wasted tokens with no loss in quality
>
> — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)

「最後に検証ステップを入れる」「subagent に検証させる」といった指示を**削除する**と、品質を落とさずに無駄なトークンが減る、という主張です。

プロンプトエンジニアリングの文脈では珍しい方向の助言なので、本当にそうなるのかを Claude Code のサブスクリプションだけで実測しました。結論から言うと、**ツール呼び出しが約2.2倍、出力トークンが約1.4倍に増えて、テスト通過数は1点も変わりませんでした。**

前半で API とドキュメントの変更点を整理し、後半で実測の手順と結果を書きます。実測部分は再現できるようにスクリプトごと載せています。

## スペックと価格

| 項目 | Claude Opus 5 | Claude Opus 4.8 |
|---|---|---|
| API モデルID | `claude-opus-5` | `claude-opus-4-8` |
| コンテキスト | 1M トークン | **1M トークン（同じ）** |
| 最大出力 | 128k トークン | **128k トークン（同じ）** |
| 価格（入力 / 出力） | $5 / $25 | **$5 / $25（同じ）** |
| adaptive thinking | あり | **あり（同じ）** |
| effort の段階 | low / medium / high / xhigh / max | **同じ** |
| **thinking のデフォルト** | **ON** | OFF |
| **知識カットオフ** | **2026年5月** | 2026年1月 |

ハードウェア的なスペックはほぼ据え置きです。1M トークンのコンテキストは Opus 4.6 / 4.7 / 4.8、Sonnet 4.6 / 5 でも同じで、**beta ヘッダは不要、課金も標準価格**です。200k に留まっているのは Sonnet 4.5 や Haiku 4.5 といった旧世代のほうです。

Opus 5 のドキュメントには「1M がデフォルトかつ最大で、これより小さいコンテキストのバリアントは存在しない」と書かれていますが、これは 4.8 からの変更点ではなく仕様の確認です。**「Opus 5 で 1M になった」と紹介している記事を見かけたら疑ってください。**

したがって移行で見るべきは、スペック表に出てこない thinking のデフォルト、effort の推奨、そして挙動の変化になります。

Fast mode は $10 / $50 で、Claude API のみの提供です。Amazon Bedrock / Google Cloud / Microsoft Foundry では現時点で使えません。

モデル自体は Claude API のほか、Amazon Bedrock（`anthropic.claude-opus-5`）、Google Cloud、Microsoft Foundry で利用できます。Opus 4.8 も引き続き併存しているので、移行は急がなくても大丈夫です。

## 破壊的変更は2つ

移行時に壊れる可能性があるのは次の2点です。

### 1. thinking がデフォルトONになった

Opus 4.8 では `thinking` を指定しないとき、thinking なしでリクエストが走っていました。Opus 5 では**同じリクエストが thinking ありで走ります**。`thinking: {"type": "adaptive"}` という書き方は引き続き有効で、デフォルトと同じ意味になります。

実害が出るのは `max_tokens` です。`max_tokens` は thinking と応答テキストを合わせた出力全体に対する上限なので、4.8 で「thinking なし」を前提に切り詰めていた場合、**応答が途中で切れる**可能性があります。移行時は必ず見直してください。

### 2. thinking の無効化が effort `high` 以下に制限された

```python
# Opus 5 では 400 エラー
client.messages.create(
    model="claude-opus-5",
    thinking={"type": "disabled"},
    output_config={"effort": "xhigh"},   # xhigh / max との組み合わせは不可
    ...
)
```

`thinking: {"type": "disabled"}` が受け付けられるのは effort が `high` 以下のときだけです。`xhigh` または `max` と組み合わせると 400 エラーになります。4.8 では effort と独立していたので、ここは明確な破壊的変更です。

チェックはリクエスト単位で行われます。会話の途中で effort を上げた1リクエストだけが落ちる、という壊れ方をするので気づきにくいです。

対処は2択です。thinking を無効のままにするなら effort を `high` 以下に下げる。effort を維持するなら `thinking` フィールドを外す。

### thinking を切ると、ツール呼び出しが黙って実行されなくなる

ここが移行で一番怖いところです。公式ドキュメントによれば、thinking を無効にした Opus 5 には2つのアーティファクトが出ることがあります。

**ツール呼び出しがテキストになる。** モデルが `tool_use` ブロックではなく、ユーザー向けの本文にツール呼び出しを書いてしまうことがあります。**ターンは正常終了し、エラーも出ず、そのツールは実行されません。** さらにエージェントループでは、漏れたテキストが会話履歴に残るため、以降のターンにも影響します。検索のようなツール多用のワークロードで起きやすいとされています。

**内部XMLタグが出力に漏れる。** `<thinking>` タグなどが可視の応答に混じることがあります。

公式の第一推奨は「thinking は切らず、effort を下げてトークンを制御する」です。ほとんどのタスクでは、**thinking 有効・effort `low` のほうが、thinking 無効の同程度のコストより良い結果になる**と説明されています。

なお、緩和策として反直感的な注意が2つ書かれています。システムプロンプトに「思考するな」「推論するな」というルールがあると**タグ漏れはむしろ悪化する**ので削除すべきこと。そして `<thinking>` のようにタグ名を名指しする指示は、一般的な形（内部タグを出力に含めない）より効果が薄いことです。

:::message
この挙動は公式ドキュメントの記述です。筆者は API キーを用意していないため未実測です。後述する実測パートは Claude Code のサブスクリプション経由で行っており、そこでは `thinking: disabled` を指定する手段がありません。
:::

## 追加された機能

### プロンプトキャッシュの最小長が 1,024 → 512 トークン

キャッシュ可能なプロンプトの最小長が半分になりました。**コードを一切変えなくても**、4.8 では短すぎてキャッシュできなかったプロンプトがキャッシュ対象になります。地味ですが、短いシステムプロンプトで大量にリクエストを投げるワークロードには効きます。

### 会話途中のツール変更（beta）

```
anthropic-beta: mid-conversation-tool-changes-2026-07-01
```

会話のターン間でツールを追加・削除しても**プロンプトキャッシュが維持される**ようになりました。従来はツールリストを変えるとキャッシュが壊れるため、セッション中は固定のツールリストを送り続ける必要がありました。長時間動くエージェントには効く変更です。

### `fallbacks` の `"default"` モード

```
anthropic-beta: server-side-fallback-2026-07-01
```

`fallbacks` パラメータに `"default"` モードが追加され、拒否のカテゴリごとに Anthropic 推奨のフォールバックモデルが適用されるようになりました。自前でモデルリストを保守する必要がなくなります。旧ヘッダ（`server-side-fallback-2026-06-01`）は明示的なリストのみ受け付けます。

## effort の推奨が4.7 / 4.8から逆転している

見落としやすいのがここです。同じ effort パラメータでも、公式の推奨する出発点が世代で逆になっています。

| モデル | 公式の推奨する出発点 |
|---|---|
| Opus 4.7 / 4.8 | コーディング・エージェント用途は **`xhigh` から始める** |
| **Opus 5** | **デフォルトの `high` から始め、`low` と `medium` を惜しみなく使う** |

ドキュメントは、以前のモデルから effort 設定を引き継いでいる場合、**使い回さず自分の eval でスイープをやり直すこと**を明示的に求めています。

もう1点、`effort` は thinking の量を制御するもので、**可視の応答の長さは縮めません**。応答が長いと感じたら effort ではなくプロンプトで長さを指示する必要があります。

## コードを変えなくても気づく挙動の変化

API を変えなくても体感が変わるポイントが公式にまとまっています。移行時のチェックリストとして使えます。

| 変化 | 対応 |
|---|---|
| 応答が長くなる / 書き出すファイルも長くなる | 簡潔さと長さを明示的に指示する（effortでは縮まない） |
| エージェント作業中のナレーションが増える | 更新の頻度と形を具体的に記述する |
| **指示しなくても自己検証する** | **「最後に検証ステップを」「subagentで検証を」という既存の指示を削除する** |
| subagent への委譲が増える | 委譲する条件を明示するか、ハーネス側で起動数に上限を設ける |
| タスクのスコープを勝手に広げる | スコープを制約するプロンプトを追加する |
| 自己訂正のナレーションが増える | 訂正を「結論が変わる場合だけ」に限定する |

注目したいのは、**Opus 4.8 では subagent への委譲を促すプロンプトが有効だったのに、Opus 5 では抑える側に反転している**点です。4.8 向けにチューニングしたプロンプト資産が、そのまま移行コストに変わります。

## 実測: 検証指示を残すと何が起きるか

ここからが本題です。「検証指示を消すとトークンが減り、品質は落ちない」を自分で測ります。

### 何が測れて、何が測れないか

Claude Code のサブスクリプションで検証できる範囲には明確な線があります。

| 検証したいこと | サブスクで可能か | 理由 |
|---|---|---|
| 検証指示のトークンコスト | ✅ 可能 | `--append-system-prompt` と `--output-format json` で測れる |
| effort による差 | ✅ 可能 | `--effort low\|medium\|high\|xhigh\|max` が使える |
| Opus 5 と 4.8 の比較 | ✅ 可能 | `--model` で両方指定できる |
| thinking 無効時の挙動 | ❌ 不可 | Claude Code に `thinking: disabled` 相当のフラグがない |
| beta ヘッダを使う機能 | ❌ 不可 | `--betas` は help に「API key users only」と明記されている |
| キャッシュ最小長512 | ❌ 実質不可 | システムプロンプトが常時20万トークン規模で、512の境界を分離できない |

サブスクリプションの OAuth 認証で raw な Messages API を叩くのはサポートされていないので、❌ の項目には別途 API クレジットが必要です。

### 測定対象のフィクスチャ

`cart/` という小さな Python パッケージを用意しました。標準ライブラリの `unittest` だけで動くので追加インストールは不要です。

- 意図的なバグ6個（割引計算、税計算、在庫の加算 / 既定値 / 境界条件）
- 未実装の関数1個（`apply_bulk_discount`、docstring に仕様を記載）
- テストは29個。手つかずの状態で **12/29 パス（17失敗）**

先に参照解を書いて **29/29 パス**することを確認しています。テスト自体が壊れていないことを保証するためです。ここを飛ばすと「モデルが悪いのかテストが悪いのか」が切り分けられなくなります。

タスクのプロンプトは全条件で共通です。

```text
cart/ パッケージにバグがあり、tests/ のテストが失敗しています。
`python3 -m unittest discover -s tests -t .` を実行し、すべてのテストが通るように
cart/ 配下のコードを修正してください。
cart/orders.py の apply_bulk_discount は docstring の仕様どおりに実装してください。
tests/ 配下のファイルは変更しないでください。
```

### 条件

2×2 のマトリクスを各3回、計12ラン回しました。effort は `high` に固定です。

`legacy` 条件だけに、`--append-system-prompt` で次を追加します。公式ドキュメントが「Opus 5 では削除せよ」と名指ししている種類の指示そのものです。

```text
作業の最後には必ず検証ステップを入れてください。
非自明なタスクでは、実装後に必ず自分の変更を再確認してください。
検証には subagent を使って独立にチェックさせてください。
回答する前に必ずダブルチェックしてください。
```

実行はこの形です。

```bash
claude -p --model claude-opus-5 --effort high --output-format stream-json --verbose --permission-mode acceptEdits
```

### 公平性のために入れた仕掛け

測定を信じられるものにするために、いくつか仕掛けを入れています。

- **各ランは新しいフィクスチャのコピーで開始する**
- **採点前に `tests/` を必ず原本に戻す**。テストを書き換えて通す抜け道を塞ぎます。改変があれば記録に残します
- **条件は交互に実行する**。時間帯によるサーバ側の状態変化が特定の条件に偏らないようにします
- **権限拒否の回数を毎ラン記録する**（後述）

### ハマった罠1: `--allowedTools` が末尾のプロンプトを飲み込む

最初のランが全部これで落ちました。

```bash
# 動かない: プロンプトが --allowedTools の引数として食われる
claude -p --allowedTools "Read Edit Bash(python3:*)" "タスク本文"
# → Error: Input must be provided either through stdin or as a prompt argument
```

`--allowedTools` は可変長引数（`<tools...>`）なので、後ろに置いた位置引数のプロンプトまで吸い込みます。プロンプトは stdin から渡すのが安全です。

```python
subprocess.run(cmd, cwd=run_dir, input=TASK, capture_output=True, text=True)
```

### ハマった罠2: subagent は `Agent` という名前で記録される

`stream-json` の `tool_use` ブロックを集計するとき、subagent の起動を `Task` という名前で数えていたら、ずっと0でした。実際には **`Agent`** という名前で記録されます。危うく「Opus 5 は subagent を起動しなかった」と誤った結論を書くところでした。

```python
SUBAGENT_TOOL_NAMES = ("Agent", "Task")
```

### ハマった罠3: Bash の許可を絞ると測定が歪む

これが一番厄介でした。安全のため Bash の許可を `Bash(python3:*)` だけに絞ったところ、モデルが投げた `for f in ...; do cat -n "$f"; done` のような複合コマンドが拒否されました。

問題は、**拒否が両条件に均等に降ってこない**ことです。legacy 条件のほうが探索を多くするぶん拒否を食らいやすく、その再試行がトークンとして計上されます。つまり「legacy はトークンを食う」という結論が、ハーネスの都合で水増しされます。

許可リストに `cat` や `for` を足しても解決しませんでした。前方一致のパターンでは、シェルのループや `;` 連結を含む複合コマンドを表現できないためです（拒否は2件から3件に増えました）。

最終的には、**タスク文のほうに制約を書いて吸収**しました。両条件に同一の文を足すので、差分としての交絡になりません。

```text
なお、この環境の Bash はシンプルな単一コマンドのみ許可されています。
for ループ、; や && による連結、複数行コマンドは拒否されるので使わないでください。
ファイルを読むときは Bash ではなく Read ツールを使ってください。
```

これで権限拒否は 21ラン中1件まで落ちました。

### 結果1: 品質は完全に同一、コストだけが増える

**21ラン全てが 29/29 パス**しました。テストの改変もゼロです。つまり検証指示による品質向上は、この実験では**まったく観測されませんでした**。

その上でコストは増えます（中央値、n=3）。

| 指標 | Opus 5 clean → legacy | Opus 4.8 clean → legacy |
|---|---|---|
| 出力トークン | 4,459 → **6,146（+38%）** ✅ | 4,466 → 5,063（+13%）⚠️ |
| ツール呼び出し | 16 → **36（+125%）** ✅ | 14 → 23（+64%）✅ |
| ターン数 | 17 → 19（+12%）✅ | 15 → 16（+7%）⚠️ |
| 実時間 | 68秒 → **285秒（+317%）** ✅ | 70秒 → 122秒（+75%）✅ |
| コスト換算 | $0.49 → **$1.40（+185%）** ✅ | $0.56 → $0.81（+44%）✅ |
| subagent 起動 | 0 → 1 | 0 → 1 |

✅ は3ランの実測範囲が重ならなかったもの、⚠️ は重なった（＝誤差の範囲）ものです。中央値の差だけを見て「◯%増えた」と書くと、ばらつきの中に埋もれた差まで主張してしまうので、範囲の重なりを併記しています。

**注目すべきは非対称性です。** Opus 4.8 の出力トークン増加は clean [4,439-4,538] と legacy [4,445-5,389] で範囲が重なり、誤差の範囲でした。一方 **Opus 5 は [4,214-4,463] と [5,601-6,721] で完全に分離**します。

同じ指示が、4.8 ではほぼ無害で、Opus 5 でだけ確実にトークンを食います。公式ドキュメントが「Opus 5 では削除せよ」とモデルを名指ししている理由が、数字として出てきました。

### 結果2: このタスクでは xhigh は何も買っていない

effort スイープの結果です（Opus 5、検証指示なし、各3回）。

| effort | 出力トークン | ツール呼び出し | 実時間 | 品質 |
|---|---|---|---|---|
| `low` | **3,139** | 13 | **48秒** | 3/3 グリーン |
| `medium` | 3,848 | 15 | 57秒 | 3/3 グリーン |
| `high`（既定） | 4,459 | 16 | 68秒 | 3/3 グリーン |
| `xhigh` | 5,170 | 17 | 68秒 | 3/3 グリーン |

出力トークンは `low` → `medium` → `high` → `xhigh` と綺麗に単調増加し、隣接するどの組み合わせでも範囲が分離しました。effort パラメータがちゃんと効いていることは確認できます。

一方で品質は全段で同じです。**`low` は `high` に対して出力トークンが30%少なく、実時間が29%短いのに、テスト通過数は同じ**でした。

そして `high` → `xhigh` では、出力トークンが +16% 増える以外、**ツール呼び出し・ターン数・実時間・コストが全て誤差の範囲**でした。このタスクに関する限り、`xhigh` に払う理由は実測上ありませんでした。4.7 / 4.8 の「コーディングは xhigh から」をそのまま持ち込むと、得るものなくトークンだけ増えることになります。

### この実測の限界

数字を使う前に、限界を明示しておきます。

1. **タスクが1種類で、易しめです。** 29テスト中17失敗を直す規模で、全 effort が満点を取ってしまったため、**`low` が破綻する境界は測れていません**。「`low` で十分」と一般化はできず、「このクラスのタスクでは `low` で足りた」までです
2. **n=3 です。** 範囲の重なりで足切りはしましたが、統計的検定はしていません
3. **実時間のばらつきが大きいです。** clean 条件単体でも 58〜114秒とばらつきました。範囲自体は重ならないので方向は確かですが、「+317%」という倍率の精度は低く、そのまま引用するのは避けるべきです
4. **キャッシュ読み込みトークンは指標として使えませんでした。** 同一条件の反復で最大214%ばらついたため、集計から除外しています
5. **529 Overloaded で4ラン失敗し、再実行しています。** サーバ側の一時障害でモデルの品質失敗ではないため除外しましたが、除外の判断が入っていることは明記しておきます
6. **Claude Code 経由なので絶対値は大きく出ます。** システムプロンプトが常時20万トークン規模でキャッシュに載っているため、素の API より入力側が大きくなります。比較には使えますが、絶対値を API のコスト見積もりに転用しないでください

## 移行チェックリスト

最後に、移行時に見るべき点をまとめます。

**API を変える**

- [ ] モデルIDを `claude-opus-4-8` から `claude-opus-5` に変更する
- [ ] `max_tokens` を見直す（thinking がデフォルトONになり、出力全体の上限に効くため）
- [ ] `thinking: {"type": "disabled"}` を使っているなら、effort が `high` 以下か確認する（`xhigh` / `max` は400エラー）

**プロンプトから消す**

- [ ] 「最後に検証ステップを入れる」系の指示
- [ ] 「subagent で検証させる」系の指示
- [ ] 「ダブルチェックしてから答える」「再確認する」系の指示
- [ ] 4.8 向けにチューニングした vision の回避策
- [ ] ハーネス側に組み込んだ独立の検証ステップ

**プロンプトに足す**

- [ ] 簡潔さの指示（effort では応答は縮みません）
- [ ] 書き出すファイルの長さの指示
- [ ] ナレーションの頻度と形の指示
- [ ] スコープを広げないための制約
- [ ] subagent の委譲条件、または起動数の上限

**測り直す**

- [ ] effort を以前のモデルから引き継がず、自分の eval でスイープし直す

## まとめ

Claude Opus 5 のスペックは Opus 4.8 とほぼ同じです。価格も、1M コンテキストも、128k の最大出力も据え置きで、破壊的変更は「thinking がデフォルトON」と「`xhigh` / `max` では thinking を切れない」の2点に絞られます。

ただし移行作業の重心はそこではありませんでした。4.8 時代に良かれと思って書いた検証指示・subagent 指示・effort 設定が、Opus 5 では素直に負債になります。実測では、検証指示を残したまま移行すると **ツール呼び出しが約2.2倍、出力トークンが約1.4倍、実時間が4倍前後に増えて、テスト通過数は1点も変わりません**でした。しかも同じ指示を Opus 4.8 に与えた場合、トークンの増加は誤差の範囲に収まります。この浪費は Opus 5 固有のものです。

プロンプトを磨き込むほど良くなる、という前提が効かない場面があります。モデルが自分でやるようになったことは、指示から外す。移行のたびにこの棚卸しが要る、というのが今回の実感でした。
