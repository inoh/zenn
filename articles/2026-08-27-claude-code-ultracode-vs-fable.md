## はじめに

2026年後半のClaude Codeには、難しいタスクに対する攻め方が2つあります。

ひとつは**モデルの格を上げる**こと。Claude Fable 5という、Opusの上位に位置づけられたモデルを使います。もうひとつは**エージェントの数を増やす**こと。`ultracode` を有効にして、Claude Codeに数十体のサブエージェントを編成させます。

前者はトークン単価が2倍、後者は単価は据え置きでトークン消費が何倍にもなります。どちらも「高い」のですが、高くなる理由がまったく違います。

この記事では、まず両者の正体を公式ドキュメントとchangelogで正確に押さえた上で、同じ脆弱性監査タスクを「Fable 5単騎」と「Opus 5を16体にfan-outさせた編成」の両方に解かせ、検出率・誤検出・トークン消費を実測しました。

結論から言うと、**このタスクでは単騎のほうが安く、そして正確でした**。ただしそれは「群れが常に劣る」という意味ではありません。何が起きたのかを順に見ていきます。

## ultracodeは「モデル」でも「賢さの目盛り」でもない

まず、よくある誤解を潰しておきます。`ultracode` はモデル名ではありませんし、`effort` の最上位でもありません。

公式ドキュメントの定義はこうです。

> Ultracode is a Claude Code setting that combines `xhigh` reasoning effort with automatic workflow orchestration.

つまり、**`xhigh` の推論努力度**と、**dynamic workflowの自動編成**という2つの要素の組み合わせです。`effort` の階梯は `low` / `medium` / `high` / `xhigh` / `max` であって、`ultracode` はそこには入りません。実際、`claude --help` を見ると次のように書かれています。

```
--effort <level>    Effort level for the current session
                    (low, medium, high, xhigh, max)
```

`ultracode` の名前がありません。それでも `claude --effort ultracode` は引数としては受理されます。CLIのヘルプに載っている「モデルの努力度」と、Claude Codeの機能設定としての `ultracode` が別レイヤーだということが、ここに現れています。

### dynamic workflowとは何か

`ultracode` の後半分である dynamic workflow は、**Claudeがその場で書いたJavaScriptを、ランタイムがバックグラウンドで実行する**仕組みです。スクリプトが `agent()` を呼んでサブエージェントを起動し、`pipeline()` や `parallel()` でそれらを並べます。

重要なのは、オーケストレーションの主体がClaudeの会話ターンではなく**スクリプト**になる点です。公式ドキュメントの比較表では、この違いがこう整理されています。

| | サブエージェント | ワークフロー |
|---|---|---|
| 次に何を実行するか決めるのは | Claude（ターンごと） | スクリプト |
| 中間結果の置き場所 | Claudeのコンテキストウィンドウ | スクリプト変数 |
| 規模 | ターンあたり数個 | 1ランあたり数十〜数百 |

中間結果がコンテキストに載らないので、Claudeの手元には最終的な答えだけが残ります。これが「1回の会話では抱えきれない規模」を扱えるようにしている仕掛けです。

### `workflow` から `ultracode` へ

この機能の名前は途中で変わっています。`anthropics/claude-code` のCHANGELOGを実際に引いて確認しました。

```bash
gh api repos/anthropics/claude-code/contents/CHANGELOG.md --jq '.content' | base64 -d | grep -n -i 'ultracode'
```

追えたのは次の流れです。

- **v2.1.154**: dynamic workflowsが導入される
- **v2.1.157**: プロンプト中の "workflow" という単語でワークフローが起動するのを止める設定が `/config` に追加される
- **v2.1.160**: トリガーキーワードが `workflow` から `ultracode` に改名される
- **v2.1.170**: Claude Fable 5に対応

v2.1.157の存在が面白いところで、「workflow」という一般的な単語をトリガーにしたせいで誤爆が多発したのだろうと想像がつきます。その反省を経て、まず使わない造語である `ultracode` に落ち着いたわけです。

なお、キーワードの発火条件も後から絞られています。v2.1.210以降、`ultracode` が実際にワークフローを起動するのは**人間が自分でタイプしたプロンプトの場合だけ**です。`-p` で渡したプロンプト、スケジュールされたタスク、webhookペイロード、PRコメントの中継では起動しません。CHANGELOGにはこう記録されています。

> Fixed the `ultracode` keyword opt-in firing on non-human-originated input such as webhook payloads and relayed PR comments

PRコメントに `ultracode` と書いただけで数十体のエージェントが動き出す、という事故を防ぐ修正です。

### 規模の上限

ランタイム側の制約も明示されています。

- 同時実行は**最大16エージェント**（CPUが少ない環境ではさらに減る）
- 1ランあたり合計**1,000エージェント**が上限
- サイズガイドラインのデフォルトは `medium`（15体未満を目安）

そして、25体を超えるか予測トークンが150万を超えると「Large workflow」の警告が出ます。ただし**ultracodeが有効なセッションではこの警告は出ません**。大きなランに同意した状態だとみなされるからです。

## Fable 5は「Opusの上」に置かれたモデル

もう一方の選択肢がClaude Fable 5です。2026年6月9日に発表されました。

Anthropicの説明では、Fable 5とMythos 5は同じ基盤モデルで、safeguardsの有無で区別されます。Mythos-classというのは「a tier of Claude models that sit above our Opus class in capability」、つまりOpusクラスの上に位置する階層のことです。Fable 5はそのうち「a Mythos-class model that we've made safe for general use」と説明されています。

安全対策として、サイバーセキュリティ・生物学/化学・蒸留攻撃の3領域でフォールバック機構が働きます。発表では「more than 95% of Fable sessions involve no fallback」とされています。

APIレベルでも、Opus系とは扱いが違う点がいくつかあります。

- **thinkingは常時ON**。`thinking` パラメータは省略するか `{type: "adaptive"}` にします。`{type: "disabled"}` も `budget_tokens` も400エラーになります
- 深さの制御は `output_config.effort`（`low` 〜 `max`）で行います
- 生の思考連鎖は返りません
- `refusal` という `stop_reason` を返しうるので、`fallbacks` の設定が推奨されます
- ゼロデータ保持の組織では利用できません（30日保持が必須）

`effort` が `xhigh` まで対応しているということは、**Fable 5でもultracodeが使える**ということでもあります。この記事の比較は「Opus+群れ vs Fable単騎」ですが、本来の選択肢は2×2のマトリクスです。

## コスト構造は対称ではない

価格を並べます。

| モデル | 入力 | 出力 |
|---|---|---|
| Claude Fable 5 | $10 / MTok | $50 / MTok |
| Claude Opus 5 | $5 / MTok | $25 / MTok |

Fable 5がちょうど2倍です。そしてOpus 5の発表では、Fable 5との関係がこう表現されています。

> close to the frontier intelligence of Claude Fable 5 at half the price

具体的なベンチマーク数値については注意が必要です。ネット上には「SWE-bench Verified 96.0% vs 95.0%」といった数字が流通していますが、**Anthropicの公式発表ページには具体的スコアが載っていません**。載っているのは相対表現だけです。CursorBench 3.2について「at max effort, the model performs within 0.5% of Fable 5's peak score, but at half the cost」、OSWorld 2.0について「surpassing Fable 5's best result at just over a third of the cost」といった書き方です。この記事でも数値の引用は避けます。

ここで、コスト構造の非対称性が効いてきます。

- **Fable 5単騎**を選ぶと、コストは「単価2倍 × 1体分のトークン」
- **Opus 5でultracode**を選ぶと、コストは「単価1倍 × N体分のトークン」

そして、ワークフローのサブエージェントは**セッションのモデルを継承します**（`CLAUDE_CODE_SUBAGENT_MODEL` 環境変数かスクリプト側の指定で上書きは可能）。つまりOpusセッションでultracodeを回せば、Opus単価でトークンが物量的に増えるという構造になります。

単価の差は固定で2倍。一方エージェント数は数体から数百体まで動きます。**どちらが高くつくかは、タスクが何体を必要とするかで決まる**わけです。これは机上で決められる話ではないので、実際に測ってみました。

## 実測: 同じ脆弱性監査を単騎と群れで解かせる

### フィクスチャ

Express風のルートハンドラを8ファイル用意し、意図的に脆弱性を6件仕込みました。合計228行です。

| ファイル | 仕込んだ欠陥 |
|---|---|
| `orders.js:11` | IDOR（`GET /orders/:id` に所有者チェックがない） |
| `admin.js:11` | 権限チェック漏れ（`suspend` だけ `requireAdmin` がない） |
| `search.js:9` | SQLインジェクション（`db.raw` に検索語を直結） |
| `profile.js:17` | mass assignment（`req.body` のキーをSET句に展開。カラム名経由のSQLインジェクションにもなる） |
| `files.js:10` | パストラバーサル（`path.join` に生の `req.params.name`） |
| `webhooks.js:11` | タイミング攻撃（HMAC署名を `!==` で比較） |
| `health.js` / `products.js` | なし（誤検出を測るための対照） |

意地悪な作りにしてあります。たとえば `orders.js` はDELETEには所有者チェックがあるのにGETにはない、`files.js` はthumb側だけ `path.basename` を通している、`webhooks.js` はshipping側だけ `crypto.timingSafeEqual` を使っている、という具合です。「ファイル全体を斜め読みして雰囲気で判定する」と、対照側を誤検出するか、本命を見落とすようにしてあります。

### 条件

**条件A（単騎）**: Fable 5のエージェント1体に、ディレクトリごと監査させる。

**条件B（群れ）**: Opus 5でファイルごとに1体ずつ監査エージェントをfan-outし、上がってきた指摘1件ごとに**敵対的検証エージェント**を立てて反証を試みる。公式ドキュメントがcanonicalパターンとして挙げている構成です。検証側のプロンプトには「確信が持てなければ refuted=true をデフォルトにせよ」と書いてあります。

両条件のプロンプトは、監査対象・報告フォーマット・「クリーンなファイルもある」という注意書きまで揃えました。

### 結果1: 検出品質は完全に同じだった

まず検出結果です。

| | Fable 5 単騎 | Opus 5 × 16体 |
|---|---|---|
| 仕込んだ欠陥の検出 | 6 / 6 | 6 / 6 |
| 報告件数 | 7件 | 8件 → 検証後7件 |
| 誤検出 | 0件 | 0件（1件は検証で除去） |

どちらも**6件すべてを検出し、誤検出はゼロ**でした。報告が7件になっているのは、両者とも `profile.js` の1箇所をSQLインジェクションとmass assignmentの2件に分けて報告したためです。これは分類として妥当な判断です。

対照として置いたクリーンなファイルも、両者とも正しく素通りしました。Fable 5は報告の最後に「exploitableな問題のないファイル」として `health.js`、`products.js`、`files.js` のthumbハンドラ、`orders.js` のDELETE、`webhooks.js` のshippingハンドラを明示的に列挙しており、対照を対照として認識していたことがわかります。群れ側も `health.js` と `products.js` の担当エージェントは空の結果を返しました。

### 結果2: 敵対的検証は仕事をした。ただし自分が出したノイズに対して

群れ側だけが出した8件目は、`profile.js:17` の `RETURNING *` によって機密データが露出する、という指摘でした。これは検証フェーズで反証されています。

検証エージェントの言い分はこうです。フィクスチャに登場する `users` のカラムは `id`、`email`、`display_name`、`role`、`created_at`、`suspended`、`avatar_url` だけで、パスワードハッシュのような機密カラムが存在する根拠はコード中にありません。しかもこのハンドラは `WHERE id = $1` に `req.user.id` を渡しているので、返るのは呼び出し元自身の行だけです。したがって「第三者への露出」は起きない、というわけです。

そして検証エージェントは親に対して、「同じ行の本当に深刻な問題は別の2件（SQLインジェクションとmass assignment）のほうだ」と付け加えています。

敵対的検証は確かに機能しました。しかし冷静に見ると、**この弱い指摘を出したのも群れ自身**です。単騎ははじめからそんな指摘をしていません。つまりここで起きたのは、群れが増やしたノイズを群れが自分で掃除した、という自己完結でした。品質の最終地点は単騎と同じです。

### 結果3: コストは15倍。しかも「頭数」でほぼ決まっていた

Claude Codeが報告したトークン消費です。

| | Fable 5 単騎 | Opus 5 × 16体 |
|---|---|---|
| トークン | 40,819 | 610,333 |
| ツール呼び出し | 2回 | 54回 |
| 所要時間 | 59.9秒 | 130.5秒 |
| エージェント数 | 1 | 16（監査8 + 検証8） |

トークンで**約15倍**です。Fable 5の単価はOpus 5の2倍なので、素のトークン単価だけで単純計算しても、なお約7.5倍は群れのほうが高くつきます。

ただしこの7.5倍という数字は上限寄りの見積もりです。両条件ともプロンプトキャッシュの読み取りが消費の大半を占めており（単騎で約83%、群れで約93%）、キャッシュ読み取りは通常の入力よりずっと安く課金されるためです。ワークフローのサブエージェントは、同一ラン内で互いのプロンプトキャッシュを読めるよう後続エージェントの起動を意図的に遅らせる仕組みを持っており、それが効いています。実際の請求額での開きは、私の環境の内訳から概算すると3〜4倍程度でした。

いずれにせよ、**品質が同一で、コストだけが数倍になった**という構図は変わりません。

そして、この実測でいちばん面白かったのはここです。16体それぞれのトークン消費を個別に集計すると、こうなりました。

```
36,993 / 37,009 / 37,099 / 37,950 / 38,259 / 38,655 / 38,774 / 38,995
39,208 / 39,741 / 39,749 / 39,937 / 40,203 / 40,396 / 41,407 / 42,652
```

最小36,993、最大42,652。**ばらつきは15%程度しかありません**。

監査エージェントは18〜37行のファイルを1つ読んで報告する仕事、検証エージェントは指摘1件の妥当性を吟味する仕事です。仕事の中身が違うのに、消費はほぼ一定でした。しかも1体あたり約39,000トークンというこの値は、**Fable 5単騎が全工程で使った40,819トークンとほとんど同じ**です。

つまり、この規模のタスクにおけるコストの正体は、タスクの難しさではなく**エージェントを1体立ち上げる固定費**でした。システムプロンプトとツール定義が読み込まれた時点で約39,000トークンが確定し、その上に載る実際の仕事は誤差の範囲だったということです。

**ワークフローのコストは、タスクの難易度ではなく頭数でほぼ決まる。**

### この実測でわかったこと、わからないこと

今回のフィクスチャは8ファイル228行、1つのコンテキストウィンドウに余裕で収まるサイズでした。だからこそ単騎は2回のツール呼び出しで全部読み切り、ファイルをまたいだ対比まで一望できたわけです。

これは公式ドキュメントが書いていることと、そのまま一致します。

> Reach for a workflow when a task needs more agents than one conversation can coordinate

裏を返せば、**1つの会話で抱えられるタスクにワークフローを使うと、品質は変わらずコストだけが跳ね上がる**。今回の実測はその具体例になりました。

一方で、この結果から言えないこともあります。

- **500ファイルの移行**のように1コンテキストに入らない規模では、話は完全に逆転します。単騎はそもそも実行できません
- **モデルの地力そのもの**は測れていません。今回は両者とも満点だったので差が出ませんでした。もっと難しいタスクでなければFable 5の格は現れません
- 1回ずつの実行なので、**実行ごとのばらつき**は評価できていません
- 固定費約39,000トークンという値は、私の環境のシステムプロンプト・ツール構成に依存します

## どう使い分けるか

実測と公式ドキュメントを踏まえると、判断の軸は「賢さ」ではなく**タスクが1つのコンテキストに収まるか**です。

**単騎（必要ならFable 5）が向く場合**

- 対象が1コンテキストに収まる
- ファイルをまたいだ文脈の対比が要る（今回の `orders.js` のGETとDELETEの対比のような判断）
- 1回の深い推論で解ける

**ultracodeによる編成が向く場合**

- 対象が1コンテキストに入らない（大規模移行、リポジトリ全体の監査）
- 同じ処理を大量のアイテムに繰り返す
- 独立した視点でのクロスチェックに価値がある（複数の角度から案を出して突き合わせる、など）
- オーケストレーション自体を再実行可能なスクリプトとして残したい

そして両者は排他ではありません。Fable 5は `xhigh` に対応しているので、Fable 5のセッションでultracodeを有効にすることもできます。単価2倍 × 頭数という、いちばん高くつく組み合わせでもあるので、使いどころは選ぶべきですが。

コストを抑える実務的な手としては、次のあたりが効きます。

- `/config` の Dynamic workflow size を `small`（5体未満）にする
- 大きなランの前に `/model` を確認する（サブエージェントはセッションのモデルを継承します）
- スクリプト内で、機械的な段階だけ小さいモデルに振る
- いきなり全体に流さず、1ディレクトリなど狭い範囲で試して `/workflows` のトークン表示を見る

## まとめ

- `ultracode` はモデルでも effort の最上位でもなく、**`xhigh` + ワークフロー自動編成**というClaude Codeの設定です
- Fable 5はOpusクラスの上に置かれたMythos-classのモデルで、単価はOpus 5の2倍です
- 8ファイル228行の脆弱性監査で両者を比べたところ、**検出品質は完全に同一**（6/6検出・誤検出0）で、**トークンは約15倍**（キャッシュを考慮した実請求ベースでも3〜4倍）の開きが出ました
- 群れの消費は1体あたり約39,000トークンでほぼ一定でした。**コストはタスクの難易度ではなく頭数で決まります**
- 敵対的検証は機能しましたが、潰した対象は群れ自身が生んだノイズでした
- ワークフローの価値は「賢くなること」ではなく「**1つのコンテキストに入らない規模を扱えること**」にあります

難しいタスクにぶつかったとき、reflexとして `ultracode` と打つ前に、まず「これは1つのコンテキストに入るか」を自問するのがよさそうです。入るなら、頭数を増やしても買えるものはあまりありません。
